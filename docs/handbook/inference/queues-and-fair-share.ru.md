# Очереди и fair share

[English](queues-and-fair-share.md) | [Оглавление справочника](../README.ru.md)

Когда GPU занят, кто идёт следующим, решает llm-d EPP. Он держит по очереди
на каждую полосу приоритета, а внутри полосы - по очереди на пользователя, и
отправляет запросы по сигналу насыщения из метрик движка. pat-service только
ставит метки; решения принимает EPP ([ADR 0008](../../adr/0008-per-user-fair-share.md),
[ADR 0012](../../adr/0012-graduated-band-ceiling-over-strict-priority.md)).

## Модель на одной картинке

```
запрос --(x-llm-d-inference-objective, x-llm-d-inference-fairness-id)--> EPP
                                                                          |
   полоса warm (10)    [очередь A][очередь B]   round-robin между пользователями, FCFS внутри
   полоса normal (5)   [очередь A][очередь C]
   полоса demoted (1)  [очередь B]
   полоса 0 (без заголовка)[Open WebUI ...]
                                                                          |
   цикл отправки: сначала старшая полоса, при насыщении - через политику потолков
                                                                          v
                                                               под движка (один)
```

Запросы всегда принимаются в очередь (в пределах лимитов ниже). Вопрос
только в том, *когда* и *в каком порядке* они из неё выходят.

## Полос четыре, а не одна

В `config/llmd/router-nvfp4-values.yaml` в `flowControl.priorityBands`
указана одна полоса (`priority: 0`), но в работающем EPP их четыре. Полосы
10, 5 и 1 создаются во время работы из объектов `InferenceObjective`,
перечисленных в `router.inferenceObjectives` и разрешаемых в namespace
`InferencePool`. `router.inferencePool.create: true` существует только как
этот якорь; маршрут шлюза никогда не указывает на `InferencePool`.

| Полоса | Приоритет | Кто сюда попадает |
| --- | ---: | --- |
| `warm` | 10 | PAT-сессия, отправленная в движок в последние 120 с: её KV-кэш, вероятно, ещё на GPU, и обслужить её первой дёшево |
| `normal` | 5 | новая или остывшая PAT-сессия; любой запрос, когда pat-service не достучался до Valkey |
| `demoted` | 1 | пользователь с длинной серией в одной сессии или с расходом намного выше остальных активных ([правила](../pat-service.ru.md#выбор-полосы-приоритета)) |
| запасная | 0 | запросы без заголовка objective: чаты Open WebUI и всё, что не прошло через pat-service |

Старший приоритет обслуживается первым, поэтому полоса 0 стоит **ниже**
`demoted`. Отрицательные приоритеты намеренно свободны - под будущий
фоновый класс. При старте EPP пишет в лог
`"Provisioning priority band from control plane"` для 1, 5 и 10 и
экспортирует серии `llm_d_epp_flow_control_*` для всех четырёх.

Клиент не может выбрать полосу сам: значение заголовка должно быть именем
существующего `InferenceObjective`, а копии от клиента pat-service срезает.

## Справедливость внутри полосы

Во всех полосах между потоками действует `round-robin-fairness-policy`
(поток - это один `fairness_id`, то есть один пользователь Keycloak), а
внутри потока - `fcfs-ordering-policy`. У полосы 0 они заданы явно; полосы
10, 5 и 1 наследуют `flowControl.defaultPriorityBand`. Без этого значения по
умолчанию они откатывались к глобальной строгой политике, при которой один
пользователь мог вытеснить остальных внутри полосы (ADR 0008, этап 1C).

У запросов Open WebUI нет fairness id, поэтому внутри полосы 0 они делят
один поток.

## Насыщение: когда EPP придерживает запросы

EPP отправляет запросы свободно, пока `utilization-detector` не сообщит, что
пул насыщен. Он читает `/metrics` движка (глубину очереди и занятость
KV-кэша; имена метрик под движок подбирает `core-metrics-extractor` по метке
пода `llm-d.ai/engine-type`) с порогами плагина по умолчанию:

- `queueDepthThreshold: 5` ожидающих запросов в движке
- `kvCacheUtilThreshold: 0.8` занятого KV-кэша

Оба задаются через `parameters` плагина. ADR 0012 решил не поднимать
`kvCacheUtilThreshold`: давление на KV, которое до него доходило в
нагруженные дни, было настоящим.

Если EPP не может прочитать метрики эндпоинта, эндпоинт считается
**устаревшим** (stale), и EPP закрывается: в него ничего не отправляется.
Именно это ловит алерт Grafana `adr0012-stale-endpoints`
(`llm_d_epp_flow_control_stale_endpoints > 0`). Ровно к этому приводят
неверный селектор `modelServers` или метка движка; `make engine-up` держит их
согласованными.

## Между полосами: градуированный потолок

Строгий приоритет под нагрузкой навсегда отдавал бы всё `warm`, а `normal`
и `demoted` голодали бы. `soft-reflective-ceiling-policy`
(`flowControl.usageLimitPolicyPluginRef`) ограничивает полосы по рангу:

```
ceiling[i] = 1 - i * saturation / (N - 1)      i = 0 для старшей активной полосы, N активных полос
```

Полоса ниже своего потолка открыта. Полоса на потолке или выше открывается
в одних циклах отправки и закрывается в других (период `round(s / (1 - s))`),
так что младшие полосы получают убывающую долю, а не ноль. При насыщении 1.0
ждут все полосы. Политика смотрит только на порядок полос, поэтому числовые
приоритеты 10, 5, 1 настраивать не нужно. В закреплённой сборке EPP это
Alpha-плагин, и ему нужен `router.epp.flags.allow-experimental-plugins: true`.

## Лимиты очереди

| Настройка | Значение | Эффект |
| --- | --- | --- |
| `flowControl.maxRequests` | 32 | всего запросов в EPP (в очереди); сверх этого новые отклоняются |
| `flowControl.maxBytes` | 2 GiB | суммарный размер удерживаемых тел |
| `flowControl.defaultRequestTTL` | 10 мин | запрос, прождавший дольше, отбрасывается с ошибкой |
| `priorityBands[0].maxRequests` | 32 | лимит полосы 0 |
| `proxy.failOpen` | false | если EPP недоступен, запросы падают, а не идут в обход очереди |

## Скоринг

После того как flow control выпускает запрос, профиль планирования оценивает
эндпоинты-кандидаты: `queue-scorer` (вес 2), `kv-cache-utilization-scorer`
(2) и `prefix-cache-scorer` (3, предпочитает эндпоинт, у которого уже есть
префикс промпта). При одной реплике движка выбор тривиален; веса важны,
когда реплик больше.

## За чем следить

| Вопрос | Метрика (EPP `:9090/metrics`, job Prometheus `llmd-epp`) | Дашборд |
| --- | --- | --- |
| Есть ли очередь и в какой полосе | `llm_d_epp_flow_control_queue_size{priority}` | llm-d / Inference Gateway, QoS / Cluster load |
| Сколько ждут запросы | `llm_d_epp_flow_control_request_queue_duration_seconds` | там же |
| Насыщен ли пул | `llm_d_epp_flow_control_pool_saturation` | QoS / User activity |
| Задержка по пользователям | `llm_d_epp_request_ttft_seconds{fairness_id}` | QoS / User activity |
| Устаревшие эндпоинты (fail closed) | `llm_d_epp_flow_control_stale_endpoints` | алерт `adr0012-stale-endpoints` |
| Какие полосы ставит pat-service | `patsvc_requests_total{band}` | QoS / Fair share |

Часть дашбордов ещё использует устаревшие имена `inference_extension_*`; в
этой сборке EPP есть оба варианта. Как превращать эти показания в изменения:
[тюнинг](../configuration/tuning.ru.md#очереди-и-полосы).
